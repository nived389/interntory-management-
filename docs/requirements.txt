Key implementation principle
Use a transaction-ledger model plus immutable month-end snapshots. Do not directly overwrite a single stock number 
without a transaction record. This is what makes six-year reporting, audits, breakage valuation and month-to-month 
reconciliation reliable.

1. Goals and Final Scope
The system should replace the current spreadsheet-based monthly inventory process while keeping the familiar report 
layout. It must be simple enough for staff to use on mobile phones, but detailed enough for the Master user to manage 
stock, rates, reports and historical records from a laptop.
1.1 Required outcomes
 Two properties in one system: Travelicious and Travellers Cavern, selectable by all staff.
 Monthly physical inventory: each item is counted every month, with the final actual quantity becoming the next 
month's previous stock.
 Blind staff counting: staff do not see calculated stock differences while counting; the Master sees variance after 
submission.
 Automatic breakage deduction: a submitted breakage record immediately creates a stock deduction and is 
included in monthly breakage reports.
 Photo-first item records: new items include a photo; breakage records require a camera/upload photo.
 Compressed images: images are resized and compressed before upload to reduce six-year storage usage.
 Rate/value tracking: unit rates can be recorded and monthly/yearly purchase and breakage values calculated.
 Reports and exports: section-wise, property-wise and combined reports; Excel-compatible inventory export plus 
PDF reports.
 Six-year history: inventory snapshots, transactions, breakage photos and audit records retained for at least 72 
months.
 Easy expansion: sections can be added later without changing the database or redesigning the website.
1.2 Recommended improvement without changing the requested context
Separate the operational ledger from the monthly report
Staff actions (purchase/addition, damage, breakage and count) should create immutable transactions. Monthly reports are 
generated from those transactions. This avoids manual arithmetic errors and preserves the exact history even when an item 
rate, name or section changes later.

Stock privacy rule for staff
During counts and daily actions, staff see item names, photos and specifications, but not previous stock, expected stock or 
calculated difference. This creates a true blind count and prevents the system number from influencing the physical count.
3.2 Login behavior
 Single login page for both roles.
 Username/email + password; show/hide password button.
 After authentication, route automatically by role: MASTER -> Master Dashboard; STAFF -> Staff Home.
 Master account should support two-factor authentication as an optional security setting.
 Five failed attempts should trigger a short lockout/rate limit; no password should be stored in plain text.
 Session timeout can be longer on trusted staff mobiles but must require re-login for sensitive Master settings.

4. Inventory Logic, Monthly Formula and Statuses
4.1 Core monthly formula
Excel-compatible summary formula
Previous Month Stock + New Stock - Damage/Breakage = Expected Stock. Staff enters Actual physical quantity. Master 
sees Difference = Actual - Expected. When the month is closed, Actual becomes the next month's Previous Month Stock.
Measure How it is calculated Who sees it
Previous Month Stock Previous closed month Actual Master; hidden from 
staff count screen
New Stock Sum of approved/open stock-addition transactions during the month Master
Damage Sum of unusable quantity. For the Excel-compatible export this includes breakage 
deductions. Master
Breakage Qty Sum of Breakage transactions only Master; separate 
breakage report
Expected Stock Previous + New - Damage/Breakage (+/- approved adjustments/transfers) Master
Actual Physical quantity counted at month end Staff enters; Master 
sees
Difference Actual - Expected Master only
Purchase Value Sum of addition quantity x transaction unit rate Master
Breakage Value Sum of breakage quantity x unit rate captured at event Master
4.2 Month lifecycle
Status Meaning Allowed actions
OPEN Month/section available for counting Staff can count; transactions allowed
IN PROGRESS At least one count line saved Autosave and continue
SUBMITTED Staff count submitted Staff read-only; Master reviews variance
CLOSED Master finalized month Snapshot immutable; reports archived
REOPENED Master reopened with mandatory reason Changes allowed and fully audited
4.3 Important business rules
 Only one monthly count record exists for each property + section + calendar month.
 Every active item in a section must be counted, or explicitly marked Not Found / Not Applicable with a note.
 A quantity may be zero; blank is not equal to zero.
 New items added mid-month start with previous stock = 0 and their opening/new quantity appears under New Stock.
 Closed-month data cannot be silently edited. Reopening requires Master permission and a reason, and all changes 
are logged.
 If a breakage quantity is greater than available calculated stock, reject it with a generic staff-facing validation 
message that does not reveal the exact stock balance.
 Deleting an item means archive, not hard delete, so six-year history remains complete.

6. Detailed Operating Workflows
6.1 Staff breakage workflow - exact execution
1. Staff signs in and taps Report Breakage.
2. Select Travelicious or Travellers Cavern, then select the section.
3. Search/select the object by name or photo.
4. Tap camera, capture a clear photo and confirm the preview.
5. Enter broken quantity and choose a required reason. Add note when necessary.
6. Client compresses the image before upload. Server validates the upload and returns a storage key.
7. On Submit, backend starts one database transaction: create breakage_event, snapshot unit rate, create negative 
inventory_transaction, write audit log, commit.
8. If any database step fails, rollback so stock cannot be deducted without a breakage record.
9. Return success reference. Staff must not see the updated balance or variance.
10. The event automatically appears in the current month breakage report and inventory movement totals.
6.2 Monthly count workflow
11. Master/system opens the current month count for each active section.
12. Staff selects property + section and counts actual physical stock without seeing system expectations.
13. Each line autosaves. Offline/local draft support stores unsent values until connection returns.
14. Staff reviews entered actual quantities and submits the section count.
15. Master review page calculates Previous, New Stock, Damage/Breakage, Expected, Actual and Difference.
16. Master investigates differences. If correction is required, enter a reasoned adjustment transaction rather than editing 
history invisibly.
17. Master closes the month. The Actual quantity for every line becomes the immutable closing snapshot.
18. The closed Actual becomes next month's Previous Month Stock.
19. Generate and archive the section report, property report and breakage report files.
6.3 New purchase / stock addition workflow
20. Select property, section and existing item; or create a new item first.
21. Enter quantity received and unit purchase rate. Date defaults to today but can be changed by Master.
22. Optional invoice/reference note can be stored.
23. Create positive inventory transaction and purchase value = quantity x transaction rate.
24. Optionally update the item default/latest rate to this purchase rate. Store the transaction rate permanently even if the 
default rate later changes.

8. Unit Rate, Purchase Value and Breakage Value
8.1 Recommended rate model
Value Rule
Item default/latest rate Most recently accepted unit purchase/replacement rate. Editable by Master.
Stock addition rate Rate entered for that purchase transaction; never changes after submission except through an 
audited correction.
Purchase transaction value Quantity added x transaction unit rate.
Breakage event rate Snapshot the item latest/default unit rate at the moment breakage is submitted.
Breakage loss value Broken quantity x rate snapshot.
Monthly purchase value Sum of all addition transaction values in the month.
Monthly breakage value Sum of all breakage loss values in the month.
Yearly values Sum the closed monthly values; old results do not change when current rates change.
Missing-rate behavior
If an item has no rate, allow the inventory action but flag the event as RATE MISSING in Master reports. Do not assume 
zero is a real rate. The Master can later set a rate and create a controlled valuation correction if needed.

11.2 Compression specification
Step Recommended rule
Decode Read image client-side and correct orientation.
Resize Maximum long edge 1600 px for item/breakage photos; preserve aspect ratio.
Format WebP quality about 0.72 when supported; otherwise JPEG quality about 0.72.
Target size Aim for approximately 150-350 KB; hard server limit around 1 MB after compression.
Metadata Strip EXIF/GPS metadata unless explicitly needed.
Thumbnail Generate 320 px thumbnail for list/report screens.
Filename Random UUID, never trust original filename.

12. Security, Audit, Six-Year Retention and Backup
12.1 Retention policy
Data type Minimum retention Deletion rule
Monthly snapshots 72 months No automatic deletion before 6 years
Inventory transactions 72 months Archive, do not hard delete
Breakage records + photos 72 months Keep photo with event
Generated monthly/yearly reports 72 months Store immutable archived copy at month close
Audit logs 72 months minimum Master cannot edit log entries
Disabled users/items/sections History retained Soft delete / inactive status only
12.2 Security checklist
 HTTPS everywhere; secure cookies; CSRF protection where applicable; strong Content Security Policy.
 Use managed authentication (recommended Supabase Auth) and server-side role checks.
 Database Row Level Security policies restrict staff responses and mutation scope.
 Master account optional 2FA; session revocation when staff is disabled.
 Private image bucket and short-lived signed URLs.
 Input validation on client and server; rate limiting on login and upload endpoints.
 Audit every month close/reopen, adjustment, user change, item edit and report regeneration.
 Nightly database backups; keep at least 30 daily restore points plus monthly archive/export snapshots. Test 
restoration at least twice per year.
12.3 Six-year archive strategy
Keep live history queryable
Six years is only 72 monthly periods, so normal PostgreSQL can keep this data online. Do not move older years into 
spreadsheets as the primary source. Archived PDF/XLSX files are convenient copies, but the database ledger remains the 
authoritative history.
